  and stored in CSR format and X and W are dense matrices.

- Reviewed sparse versus dense matrices and learned how CSR represents a
  sparse matrix using values[], col_idx[], and row_ptr[].

- Built a small 3 x 3 CSR example and verified how to reconstruct the
  original matrix from the CSR representation.

- Implemented sparse-dense multiplication for AX and verified the result.

- Added dense matrix W and implemented the complete computation Y = (AX)W.

- Implemented the alternative associative order Y = A(XW).

- Verified that both (AX)W and A(XW) produced the same result for the
  controlled test case.

- Refactored the demonstration code into reusable sparse-dense,
  dense-dense, matrix-printing, and verification functions.

- No performance optimizations have been applied yet. The current version
  is intended to establish correctness and serve as the foundation for
  the basic sequential implementation.

Initial Sequential Timing Baseline
----------------------------------

- Added CLOCK_MONOTONIC high-resolution wall-clock timing.

- Added one untimed warm-up followed by five measured repetitions.

- Alternated the execution order of (AX)W and A(XW) between runs to
  reduce systematic ordering bias.

- Used the median of the five measured total runtimes as the primary
  comparison metric.

- Synthetic test dimensions:
      N = 4000
      F = 128
      H = 64
      16 nonzeros per row
      nnz(A) = 64000

- Compiler configuration:
      gcc -O0 -Wall -Wextra -Wpedantic -std=c11 project1.c -o project-1 -lm

- Median results:
      (AX)W = 0.130127 seconds
      A(XW) = 0.118852 seconds

- A(XW) was 1.095x faster, corresponding to an 8.66 percent lower
  runtime for this synthetic workload.

- The sparse A*X stage required 0.023028 seconds, while sparse A*(XW)
  required 0.011841 seconds.

- This result is consistent with H = 64 being half of F = 128.
  Therefore, A*(XW) processes 64 dense values per nonzero, while
  A*X processes 128 dense values per nonzero.

- The dense multiplication stages had nearly identical median runtimes:
      (AX)*W = 0.107100 seconds
      X*W    = 0.107011 seconds

- Both evaluation orders produced matching results within the specified
  floating-point tolerance.

- The five measured runs were highly consistent, indicating that the
  timing experiment was reasonably stable.

- No algorithmic, cache, or parallel optimization has been applied yet.
  These measurements establish the initial unoptimized sequential
  timing baseline using compiler optimization level -O0.

GCC Vectorization Analysis
--------------------------

- Compiled the preserved sequential benchmark using -O3 and GCC's
  vectorization diagnostic report.

- GCC confirmed that the innermost j loop of sparse_dense_multiply()
  was vectorized using 16-byte vectors.

- Since each single-precision float occupies 4 bytes, a 16-byte vector
  can operate on four float values at a time.

- GCC also reported that the sparse loop was versioned for vectorization
  because of possible memory aliasing.

- This provides direct compiler evidence that SIMD vectorization
  contributes to the large improvement observed in the sparse-dense
  kernels at -O3. The entire speedup cannot be attributed to
  vectorization alone because -O3 performs additional optimizations.

- The naive dense-dense multiplication loop was not successfully
  vectorized. GCC reported multiple nested loops and a complicated
  memory-access pattern.

- In the current i-j-k loop ordering, A[i][k] is accessed sequentially
  as k changes, but B[k][j] moves down a column of row-major matrix B.
  This produces strided memory access rather than contiguous access.

- This result identifies dense matrix multiplication as a promising
  target for the next source-code optimization experiment.

- A planned experiment is to test an i-k-j loop ordering, which places
  j in the innermost loop. This should allow sequential row access to B
  and may improve spatial locality and compiler vectorization.

Sparse Pointer-Aliasing Experiment
----------------------------------

- GCC's previous -O3 vectorization report showed that the innermost
  sparse-dense loop was vectorized using 16-byte SIMD vectors, but GCC
  also created multiple loop versions because the input and output
  pointers could potentially alias.

- Tested adding the C restrict qualifier to the CSR arrays, dense input,
  and output pointers in sparse_dense_multiply().

- The computation and loop structure were otherwise unchanged.

- GCC continued to report successful 16-byte vectorization after the
  change.

- The previous message stating that the loop was versioned for
  vectorization because of possible aliasing disappeared. This confirmed
  that restrict successfully provided stronger non-aliasing information
  to the compiler.

- A same-session alternating A/B comparison was performed between the
  original -O3 baseline and the restrict implementation.

- Original -O3 baseline sparse performance was approximately:
      A*X       = 0.00147 seconds
      A*(XW)    = 0.000564 seconds

- With restrict, sparse performance was approximately:
      A*X       = 0.00305 seconds
      A*(XW)    = 0.00150 seconds

- The restrict implementation was therefore substantially slower in
  both sparse kernels.

- Total runtime also regressed by approximately:
      5.4 percent for (AX)W
      1.7 percent for A(XW)

- The dense multiplication timings remained nearly unchanged, supporting
  the conclusion that the regression was isolated primarily to the
  modified sparse kernel.

- Result: restrict simplified the compiler's alias analysis but did not
  improve performance for this workload. The optimization will therefore
  not be retained in the best sequential implementation.

- This experiment demonstrates that an optimization that appears
  beneficial from compiler diagnostics must still be validated by
  measurement.

Sparse Feature-Blocking Experiment
----------------------------------

- Investigated feature blocking in the CSR sparse-dense multiplication.

- The original sparse loop processed all dense feature columns for each
  nonzero entry.

- The blocked implementation instead processed the dense feature
  dimension in smaller groups while traversing each sparse row.

- Tested feature block sizes:
      16
      32
      64
      128

- Test configuration:
      N = 4000
      F = 128
      H = 64
      16 nonzeros per row
      nnz(A) = 64000
      compiler optimization = -O3

- All blocked implementations produced correct results matching both
  associative evaluation orders within tolerance.

- Measured A*X sparse-kernel times:
      block 16  = 0.001613 seconds
      block 32  = 0.001315 seconds
      block 64  = 0.001259 seconds
      block 128 = 0.001320 seconds

- Block size 64 produced the best initial A*X result.

- A same-session alternating A/B experiment was then performed between
  the original unblocked implementation and the block-64 version.

- Unblocked A*X median times:
      0.001479 seconds
      0.001468 seconds

- Block-64 A*X median times:
      0.001288 seconds
      0.001275 seconds

- Averaging the two A/B comparisons:
      unblocked A*X ≈ 0.0014735 seconds
      block-64 A*X ≈ 0.0012815 seconds

- Block size 64 reduced A*X runtime by approximately 13 percent,
  corresponding to roughly a 1.15x sparse-kernel speedup.

- For A*(XW), where the dense feature dimension is only H = 64,
  block size 64 effectively creates one feature block. Performance
  remained essentially unchanged relative to the unblocked version.

- The overall application speedup was much smaller than the sparse-kernel
  improvement because dense matrix multiplication remained the dominant
  portion of total execution time.

- Result:
      Feature blocking is beneficial for the K = 128 sparse-dense
      multiplication in this workload, with block size 64 providing
      the best tested performance.

- The experiment also demonstrates that blocking effectiveness depends
  on feature width and block size; smaller blocks introduced additional
  sparse-row traversals and did not consistently improve performance.

Feature-Blocking Vectorization Analysis
---------------------------------------

- Generated a GCC -O3 vectorization report for the best tested sparse
  feature-blocking configuration, FEATURE_BLOCK = 64.

- GCC confirmed that the innermost blocked feature loop was successfully
  vectorized using 16-byte vectors.

- GCC also continued to version the loop because of possible pointer
  aliasing.

- This is essentially the same SIMD width and aliasing behavior observed
  in the original unblocked sparse implementation.

- Therefore, the approximately 13 percent improvement previously measured
  for A*X cannot be attributed simply to enabling vectorization, because
  both the blocked and unblocked sparse loops were vectorized.

- The result is consistent with improved loop organization and data
  locality, potentially combined with other compiler code-generation
  differences. The vectorization report alone does not prove that cache
  locality is the sole cause.

- The dense matrix multiplication remained unvectorized because GCC
  continued to report a complicated memory-access pattern.

Sparse Feature-Blocking Assembly Analysis
-----------------------------------------

- A sparse-only microbenchmark was created to isolate A*X from the
  much more expensive dense multiplication stages.

- Both the unblocked and FEATURE_BLOCK=64 implementations produced
  identical checksums and passed correctness verification.

- In the repeated sparse-only benchmark, the block-64 implementation
  was approximately 2.5x faster than the unblocked implementation.

- Linux perf showed approximately:
      74 percent fewer retired instructions
      60 percent fewer CPU cycles
  for block 64 in this repeated sparse-only workload.

- GCC vectorization reports confirmed that both implementations used
  16-byte SIMD vectors and both retained runtime aliasing-related loop
  versioning.

- Therefore, the speedup was not caused simply by enabling SIMD,
  because the original implementation was already vectorized.

- Assembly inspection revealed an important code-generation difference.

- In the original unblocked kernel, GCC retained an inner SIMD loop.
  Each iteration processed four single-precision values and then
  executed pointer-update, comparison, and branch instructions.

- With F=128, this vector loop executes 32 iterations per sparse
  nonzero.

- For FEATURE_BLOCK=64, GCC generated a heavily unrolled sequence for
  the fixed 64-feature block. Sixteen 4-float SIMD groups are emitted
  at fixed memory offsets with substantially less inner-loop-control
  overhead.

- The block-64 sparse function is actually larger in static machine
  code:
      unblocked function = 253 bytes
      block-64 function  = 621 bytes

- However, the larger specialized function executes substantially fewer
  dynamic instructions, demonstrating that static code size and runtime
  instruction count are different measures.

- This provides evidence that compiler specialization and loop unrolling
  are major contributors to the feature-blocking improvement.

- Generic cache-miss measurements were variable and did not provide
  sufficient evidence to attribute the speedup specifically or solely
  to fewer cache misses.

- The approximately 2.5x sparse-only microbenchmark result is diagnostic
  evidence and is not substituted for the normal application benchmark.

- The primary application-level result remains approximately a
  13 percent reduction in A*X sparse-kernel runtime with block size 64
  for the tested N=4000, F=128, 16-nonzero-per-row workload.

- Result:
      FEATURE_BLOCK=64 remains the best tested sparse feature-blocking
      configuration for this workload and is retained as a candidate
      optimization for the best sequential implementation.

Dense Matrix Loop-Order Optimization
------------------------------------

- Investigated loop ordering for the dense matrix multiplication.

- The original implementation used:
      i -> j -> k

- In row-major storage, the innermost k loop accesses B[k][j].
  This moves down a column of B and therefore uses a strided memory
  access pattern.

- The candidate implementation changed the loop order to:
      i -> k -> j

- With j innermost, both B[k][j] and C[i][j] are traversed
  contiguously in row-major memory.

- The current best sparse settings were held constant:
      FEATURE_BLOCK = 64
      PREFETCH_DISTANCE = 2

- A controlled alternating A/B comparison was performed between
  the i-j-k and i-k-j dense implementations.

- Average dense-stage results from the controlled runs:

      (AX)*W:
          i-j-k = 0.027782 seconds
          i-k-j = 0.003385 seconds
          approximately 8.21x faster

      X*W:
          i-j-k = 0.028262 seconds
          i-k-j = 0.003251 seconds
          approximately 8.69x faster

- Dense-kernel runtime was reduced by approximately 88 percent.

- Average total method results:

      Method 1, (AX)W:
          i-j-k = 0.028918 seconds
          i-k-j = 0.004525 seconds
          approximately 6.39x faster overall

      Method 2, A(XW):
          i-j-k = 0.028846 seconds
          i-k-j = 0.003827 seconds
          approximately 7.54x faster overall

- Sparse-kernel timings remained essentially unchanged, supporting
  the conclusion that the measured improvement came from the dense
  loop-order change.

- All runs passed correctness verification.

- Result:
      The i-k-j dense loop order is retained as the current best
      dense-matrix implementation.

- The next step is to inspect GCC vectorization diagnostics to
  determine whether improved SIMD generation also contributed to
  the observed speedup.

Dense Loop-Order Vectorization Analysis
---------------------------------------

- Generated GCC -O3 vectorization reports for both dense loop orders.

- For the original i-j-k implementation, GCC reported that the dense
  loops could not be vectorized because of the complicated memory
  access pattern.

- In row-major storage, the innermost k loop accesses B[k][j], which
  moves through B with a row-sized stride rather than through
  contiguous elements.

- For the optimized i-k-j implementation, GCC successfully vectorized
  the innermost j loop using 16-byte vectors.

- A 16-byte SIMD vector contains four single-precision float values.

- The optimized j loop traverses both B[k][j] and C[i][j]
  contiguously in memory.

- GCC continued to use runtime loop versioning because of possible
  pointer aliasing.

- The compiler report therefore confirms that the loop-order change
  both improves the row-major memory-access pattern and enables SIMD
  vectorization of the dense inner loop.

- This provides compiler evidence supporting the approximately
  8x to 9x dense-kernel speedup measured in the controlled A/B tests.

- The speedup should be attributed to the combination of improved
  memory locality and successful vectorization; the current experiment
  does not isolate the contribution of either effect individually.

- Result:
      i-k-j is retained as the best tested dense loop order.

  slower than the original A*X sparse kernel.
