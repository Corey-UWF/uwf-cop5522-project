# Sequential Performance Engineering Results

## Objective

The sequential portion of the project investigates performance of:

    Y = A X W

with A stored as a sparse CSR matrix and X and W stored as dense
row-major matrices.

Both associative orders are evaluated:

    Method 1: (AX)W
    Method 2: A(XW)

The goal is not simply to produce a correct implementation. The
performance-engineering process is based on controlled experiments,
profiling/compiler analysis, correctness verification, and evaluation
of multiple optimization avenues.

---

## Measurement Method

The benchmark currently uses:

- N = 4000
- F = 128
- H = 64
- 16 nonzeros per sparse row
- 64,000 total sparse nonzeros
- one warm-up execution
- five measured executions
- median timing
- correctness verification between both associative methods

Initialization, memory allocation, output, and correctness verification
are excluded from the timed multiplication kernels.

---

## Optimization Experiments

### Compiler Optimization

The original implementation was evaluated using multiple GCC
optimization levels.

Moving from an unoptimized build to optimized builds produced a large
improvement, but compiler optimization alone did not address the main
dense-matrix performance problem.

### Pointer `restrict`

`restrict` was tested on the sparse multiplication kernel to remove
possible pointer-aliasing checks.

The compiler's vectorization report changed as expected, but measured
runtime became worse.

This optimization was rejected.

This result demonstrated that eliminating an apparent compiler concern
does not automatically produce faster code.

### Sparse Feature Blocking

The dense feature dimension of the CSR x dense multiplication was
processed in blocks.

Feature blocking improved sparse performance on the development VM.

Different block sizes were tested, including:

    16
    32
    64
    128

Block size 64 was initially strongest on the development VM, while
block size 128 proved more portable across the other systems tested.

Assembly and performance-counter experiments showed that blocking also
changed the code generated by GCC. The blocked kernel executed
substantially fewer dynamic instructions in diagnostic testing.

### Software Prefetching

Software prefetch distances were tested with the blocked sparse kernel.

Tested distances included:

    0
    1
    2
    4

On the development VM, prefetch distance 2 improved the block-64 sparse
kernel by roughly 10 percent compared with the same blocked kernel
without prefetching.

However, that result did not generalize to the other architectures.

Software prefetching was therefore classified as an
architecture-dependent optimization.

### Dense Loop Reordering

The original dense multiplication used:

    i -> j -> k

The optimized implementation uses:

    i -> k -> j

With row-major storage, the new inner j loop accesses both the B row and
the C row contiguously.

Compiler vectorization reports also showed that the optimized inner loop
was vectorized, while the original access pattern was difficult for the
compiler to vectorize efficiently.

This was the largest and most portable sequential optimization tested.

## Final Development-VM Comparison

A controlled comparison used the order:

    original
    portable v12
    portable v12
    original

Every execution passed correctness verification.

Average median results:

| Stage | Original | Portable v12 | Result |
|---|---:|---:|---:|
| A * X | 0.001475 s | 0.001449 s | about 1.76% faster |
| (AX) * W | 0.027783 s | 0.003386 s | about 8.21x faster |
| X * W | 0.028244 s | 0.003245 s | about 8.70x faster |
| A * (XW) | 0.0005635 s | 0.000562 s | essentially unchanged |
| (AX)W total | 0.029265 s | 0.0048325 s | about 6.06x faster |
| A(XW) total | 0.0288085 s | 0.0038105 s | about 7.56x faster |

Total runtime reduction was approximately:

- 83.49% for (AX)W
- 86.77% for A(XW)

## Cross-Platform Findings

### UWF cs-ssh

The dense i-k-j optimization generalized strongly.

The development-VM sparse configuration using block 64 and prefetch
distance 2 did not generalize well.

Block 128 with no software prefetch produced the strongest A*X result
among the blocked configurations tested on cs-ssh.

### PSC Bridges-2

On the AMD EPYC 7742 compute nodes, the original sparse A*X time was
approximately:

    0.001154 s

Block 128 with no prefetch measured approximately:

    0.001157 s

The difference was approximately 0.26 percent.

The block-64 configurations were slower.

The optimized dense multiplication remained strongly successful, with
approximately an 8.6x dense-kernel improvement during the controlled
comparison.

### SDSC Expanse

Expanse also uses AMD EPYC 7742 compute nodes.

The sparse A*X sweep measured approximately:

    Original CSR:               0.001010 s
    Block 64 / prefetch 2:      0.001252 s
    Block 64 / prefetch 0:      0.002061 s
    Block 128 / prefetch 0:     0.001025 s

Block 128 without prefetch was within approximately 1.5 percent of the
original sparse kernel.

The dense optimization again produced approximately an 8.5x
improvement.

frozen with:

    FEATURE_BLOCK=128
    PREFETCH_DISTANCE=0
    DENSE_IKJ=1

Source:

    project1_portable_sequential_v12.c

SHA-256:

    2deda5af6e3c95efa72e363d8812fcaabfaa757b8544f4fbd1c0341da16ce627

The dense i-k-j transformation is the strongest portable optimization
identified so far.

Sparse blocking and software prefetching require more careful
architecture- and workload-specific tuning.

## Current Limitations

The current synthetic CSR matrix has exactly 16 nonzeros per row.

This makes the workload regular and is useful for controlled sequential
testing, but it does not yet model the irregular row lengths expected
from a power-law graph.

Therefore, conclusions about sparse scheduling and load balance must not
be generalized to the final graph workload yet.

The frozen v12 program is also still a benchmark harness rather than the
final required file-driven project executable.
